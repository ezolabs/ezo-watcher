# Cloudflare tunnel for EZO Watcher

Two rungs, in order of setup cost. Both are driven by `watcher cloudflare`; the code comments in
`src/cli/cloudflare.ts` cite the API pages and their retrieval date (2026-11-04).

## Rung 0: `watcher cloudflare quick` (no account, ephemeral)

```bash
watcher run --detach
watcher cloudflare quick
```

Runs `cloudflared tunnel --url http://127.0.0.1:$WATCHER_PORT` and prints the
`https://<random>.trycloudflare.com` URL cloudflared mints. That URL is **ephemeral** (a new one each
run) and **public**, so `WATCHER_ADMIN_TOKEN` (generated by `watcher init`) is what keeps `/api`
yours. Nothing is written to a Cloudflare account. Good for a demo or a one-off share, not a home.

## Rung 1: `watcher cloudflare tunnel --hostname watch.example.com`

Idempotent hosted setup:

1. `GET /zones?name=<apex>` confirms the hostname's zone is on the account, or fails with
   `cloudflare.zone-missing`.
2. Find-or-create a remotely-managed tunnel named `watcher-<project>` (`GET/POST
   /accounts/<id>/cfd_tunnel`, body `{name, config_src:"cloudflare"}`).
3. `PUT /accounts/<id>/cfd_tunnel/<tunnel>/configurations` with the ingress:
   `[{hostname, service:"http://127.0.0.1:<port>", originRequest:{}}, {service:"http_status:404"}]`.
   The catch-all is last, as Cloudflare requires.
4. Upsert a proxied `CNAME <hostname> -> <tunnel-id>.cfargotunnel.com` in the zone.
5. `GET /accounts/<id>/cfd_tunnel/<tunnel>/token` and write the run token to `.watcher/.env`
   (`CLOUDFLARE_TUNNEL_TOKEN`, 0600) and `.watcher/data/cloudflared.token` (0600). It is never
   printed.
6. Print the run command and offer `watcher service install --with-tunnel` for a launchd/systemd
   agent.
7. With `--access-email you@example.com`: create (or find) an Access application for the hostname
   with an allow policy for that email, and make `/ingest/*`, `/mcp` and `/healthz` public path
   overrides, because senders and agents cannot do an interactive login.

`--dry-run` prints the plan and sends nothing.

## Minimum API token permissions

Create a token at <https://dash.cloudflare.com/profile/api-tokens> with:

| Scope | Permission | Needed for |
|---|---|---|
| Account | **Cloudflare Tunnel: Edit** | create/list the tunnel, PUT its configuration, read its token |
| Account | **Cloudflare Tunnel: Read** | `watcher doctor --target cloudflare` on a read-only token |
| Zone (the hostname's zone) | **DNS: Edit** | upsert the proxied CNAME |
| Zone | **Zone: Read** | find the zone id |
| Account | **Access: Apps and Policies: Edit** | only with `--access-email` |

And set `CLOUDFLARE_ACCOUNT_ID` (the account's id, not a zone id). Both go in `.watcher/.env`:

```bash
printf 'CLOUDFLARE_API_TOKEN=%s\nCLOUDFLARE_ACCOUNT_ID=%s\n' '<token>' '<account id>' >> .watcher/.env
watcher doctor --target cloudflare --hostname watch.example.com
```

## Containers (beta, for users without a host)

`deploy/cloudflare/containers/` is a template that runs the Watcher image on Cloudflare Containers
instead of on a machine you own. It is marked **beta** on purpose; read its `README.md` for the
limits that make it a poor fit for some setups (no LAN probes, cost, 6 h maximum inactivity).

## What the tunnel does not change

- The server still binds `127.0.0.1:7717` (or `WATCHER_HOST`); cloudflared is the only public door.
- `/api` stays whatever the server says. On a public hostname, keep `WATCHER_ADMIN_TOKEN` set.
- An Access app is not a substitute for the admin token: automation with a service token or the
  bypassed paths (`/ingest/*`, `/mcp`, `/healthz`) still needs the bearer the server checks.
